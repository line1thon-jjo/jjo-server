# 설정·로그아웃·회원 탈퇴 구현 및 계약 제안

이 문서는 BE1 구현 제안이다. 기존 팀 합의나 FT-009 원문을 대신하지 않는다.
저장소에는 기능명세 원문, AGENTS.md, 약관 전문이 없다. 사용자 요청의
FR-029~032 범위와 현재 코드·마이그레이션을 기준으로 구현했다.

## 사용 안내 다시 보기

프론트에서 기존 온보딩 화면을 재열람하고 설정 화면으로 돌아오면 된다.
서버 변경과 `onboarding_completed` 초기화는 필요 없다. 기존
`POST /auth/onboarding/complete`는 최초 완료를 위한 단방향 표시로 유지한다.
재열람 시 `/auth/google`의 next_step을 이용해 최초 진입 흐름으로 되돌리지 않는다.

## 약관·개인정보 처리방침

현재 서버에는 가입 동의 요청의 `service_terms`, `privacy_collection_use`,
`marketing` 및 동의 시각만 있다. 전문·버전·문서 URL·조회 API는 없다.
전문을 임의 작성하거나 빈 문서를 정상 약관으로 반환하는 API는 추가하지 않았다.
가입 프론트가 가진 확정 문서가 있다면 설정 화면도 같은 문서 소스를 참조한다.
필요 자료: 확정 서비스 이용약관, 개인정보 수집·이용 및 처리방침 전문,
문서별 버전/시행일, 공개 URL 또는 원본과 제공 주체. 서버 제공이 필요하면
이 자료와 API 계약을 프론트와 합의해야 한다.

## 로그아웃

현재 access token은 HS256 서명 JWT이며 서버 세션·refresh token·토큰 저장소·
차단 목록이 없다. 로그아웃은 프론트가 보관한 access token과 사용자/연습 캐시를
삭제하고 진행 중인 인증 요청을 중단한 뒤 로그인 화면으로 이동하는 동작이다.
프론트의 모든 저장 위치와 다른 탭의 상태도 함께 비워야 한다.

서버 무효화를 수행하지 않는 성공 전용 로그아웃 API는 만들지 않았다.
로그아웃 이전에 복사된 JWT는 만료 전까지 계속 사용할 수 있다. Google 계정의
전역 로그아웃이나 OAuth 권한 철회와도 다르다. 즉시 서버 무효화가 필요하면
토큰/세션 버전 또는 차단 목록의 지속 저장소와 모든 인증 경로의 검증 방식에
대한 별도 합의가 필요하다. 테이블·공용 설정 변경은 TEAM.md 4장 승인이 필요하다.

## 회원 탈퇴 API (신규 제안)

`DELETE /auth/me`, `Authorization: Bearer <access_token>`, 본문 없음.
사용자 ID를 받지 않으며 인증된 본인만 삭제한다. 쿼리/본문의 다른 ID는 사용하지 않는다.

- `204`, 본문 없음: DB 삭제와 모든 대상 파일 정리 완료.
- `401 ACCESS_CREDENTIAL_INVALID`: 미인증·만료·잘못된 토큰·이미 탈퇴한 사용자.
- `503 ACCOUNT_DELETION_UNCONFIRMED`: DB/저장소 준비 실패 또는 DB commit 결과 불확실.
  성공으로 표시하지 않는다. 계정이 남아 있으면 같은 인증으로 재시도할 수 있다.
  응답 유실로 실제 삭제됐을 가능성도 있으므로 재시도에서 401이면 토큰을 비운다.
  운영자는 아래 복구 명령으로 DB의 실제 상태를 다시 확인한다.
- `503 ACCOUNT_DELETED_CLEANUP_PENDING`: 계정 DB 삭제 완료, 파일 정리는 미완료.
  탈퇴 전체 완료로 표시하지 않는다. 프론트는 토큰/캐시를 비우고 정리 지연을 알린다.
  같은 토큰으로 HTTP 재시도하면 401이며 파일 정리는 서버 복구 명령이 담당한다.

오류는 기존 `{"error":{"code":"…","message":"…","fields":[]}}` 형식이다.
성공 또는 계정 삭제가 확인된 경우 프론트는 사용자 데이터·토큰을 삭제한다.
현재 보호 API는 `get_current_user`에서 DB 사용자 존재를 매번 확인하므로
탈퇴 후 기존 JWT는 만료 전이라도 거부된다. 이미 인증을 통과해 실행 중인
요청 자체를 취소하는 것은 아니다. 재가입 시 새 사용자 ID와 새 토큰이 발급된다.

API는 practice의 설정 라우터에서 조합한다. auth가 practice를 import하지 않는
팀 import 규칙을 지키며, 기존 practice router의 외부 라우트 집합에 포함하므로
공용 `app/main.py` 수정 없이 `/auth/me`에 DELETE를 추가했다.

## DB·파일 삭제 프로토콜

운영 전제: 현재 구현인 단일 서버 LocalRecordingStorage, 영속 로컬 볼륨,
PostgreSQL 기본 READ COMMITTED. 다른 저장소 구현 도입 시 journal과 recovery도
함께 교체해야 한다. 업로드 저장소와 삭제 journal은 반드시 같은 root를 사용한다.

1. 인증 후 사용자 행을 `FOR UPDATE`로 잠가 새 연습의 FK 참조와 탈퇴를 직렬화한다.
2. 소속 연습 행을 ID 순서로 잠가 기존 녹음 업로드와 직렬화한다.
3. 별도 SELECT로 최신 녹음 경로를 수집한다. 잠금 대기 중 완료된 업로드도 포함한다.
4. `uploads/recordings/.account-deletions/<UUID>.json`에 사용자 ID와 경로 목록을
   기록한다. 아래 무결성 메타데이터도 포함한다. 임시 파일→rename과 파일·디렉터리 fsync로 영속화한다.
   준비 실패 시 DB를 rollback하며 기존 음원은 건드리지 않는다.
5. 사용자만 DELETE하고 commit한다. 마이그레이션 0001의 실제 FK cascade로
   practices → recordings → reports가 삭제된다. analysis_result와 feedback은
   reports 행의 JSONB이므로 함께 삭제된다. ORM relationship cascade는 사용하지 않는다.
6. 커밋 이후 새 트랜잭션에서 사용자 부재를 확인한 뒤 파일을 지운다.
   이미 없는 파일은 성공으로 취급한다. 모든 unlink를 fsync한 뒤 journal을 제거한다.
7. 파일 정리 오류 시 503을 반환하고 journal을 남긴다. 여러 파일 중 일부만 삭제돼도
   재시도는 안전하다. DB 오류/커밋 응답 유실 시에도 음원을 먼저 지우지 않는다.

DB rollback으로 계정이 살아 있으면 복구 작업은 **모든 파일을 그대로 보존**한다.
commit 결과가 불분명할 때도 별도 연결에서 사용자 부재가 확인되어야 지운다.
DB 접속 실패 시 파일을 건드리지 않는다. rollback된 요청의 journal은 즉시
없애지 않고 보수적으로 유지한다. 이후 탈퇴 성공 시 재시도하면 같이 정리된다.
계속 살아 있는 계정의 보류 journal은 pending으로 남으므로 운영자 확인이 필요하다.
사용자 ID를 수동으로 재사용하거나 DB/볼륨을 서로 다른 시점으로 복원하면
자동 판단을 적용하지 말고 journal과 실제 참조를 대조해야 한다.

## 재시도·운영 복구

앱과 동일한 DB 설정·영속 볼륨·파일 접근 권한으로 실행한다.

```sh
python -m app.domains.practice.account_deletion
```

모든 `.json` 작업을 새 DB 세션에서 확인한다. `completed=N pending=M` 출력,
미완료/오류가 있으면 exit 1이다. 오류는 서버 로그에 남기고 내부 경로/예외를
API에 노출하지 않는다. 완료한 작업의 재실행은 안전하다. 준비 중 생긴 `.tmp`는
DB 삭제 전에만 생기므로 자동 파일 삭제 근거로 사용하지 않는다.

이 명령은 구현되어 있으나 주기 실행기는 추가하지 않았다. 배포 담당은 동일
볼륨에서 서버 재시작 후와 주기적으로 실행하고 pending·503·오류 로그를 감시해야 한다.
이를 배포 운영 절차에 반영하는 것은 협의 사항이다. journal을 웹으로 노출하거나
정리가 끝나기 전에 지우면 안 된다. 테스트는 임시 디렉터리에서만 파일을 다룬다.

## 동시 업로드·분석 및 남은 협의

- 업로드가 연습 잠금을 먼저 획득했다면 탈퇴가 기다린 뒤 새 녹음 경로까지 수집한다.
- 파일 복사 중 탈퇴가 먼저 끝나면 업로드의 재조회가 실패하고 업로드 파일을 지운다.
- 새 연습 생성이 사용자 잠금 후에 진행되면 FK 검사에서 대기하고 탈퇴 커밋 후 실패한다.
- 선행 업로드의 보상 삭제 실패, 파일 복사 후 DB 등록 전 강제 종료는 기존 업로드
  계약에도 명시된 한계다. 이 경우 탈퇴 journal이 알 수 없는 미등록 파일이 남을 수 있다.
  이번 기능이 모든 업로드 orphan을 정리한다고 보장하지 않는다. 업로드 영속 작업
  기록/고아 파일 수거는 별도 설계가 필요하다. 활성 업로드와 구별 없이 폴더를 훑어
  참조 없는 파일을 바로 삭제하는 방식은 적용하지 않았다.
- BE2 router/service 및 feedback service는 현재 주석뿐이다. 실행 중인 분석 워커나
  취소 인터페이스가 없다. 향후 BE2는 삭제된 recording에 대한 작업을 취소하고,
  FK 실패/0행 UPDATE/파일 부재를 안전하게 처리해야 한다. FK는 뒤늦은 report
  INSERT를 거부하므로 결과를 되살릴 수 없다. 메모리에 이미 읽은 음원·대본과
  외부 AI 요청은 FK로 취소할 수 없다. 임시 분석 파일·외부 작업 수명도 BE2와 협의한다.
- 현재 배포에 별도 BE2 작업 코드가 있다면 본 변경만으로 그 작업의 중단을 보장하지 않는다.
- 공용 파일, 다른 담당의 코드, 모델과 마이그레이션은 변경하지 않았다.
  `app/core/storage.py`는 TEAM.md에 명시된 BE1 담당 파일이며 이번 리뷰에서 삭제를 강화했다.

## 이번 검증 결과

분리된 일회용 PostgreSQL 16 컨테이너의 테스트 전용 DB에서 실행했다. 신규 설정
테스트는 매번 UUID 스키마에 실제 0001/0002 마이그레이션을 적용하고 제거한다.
음원과 journal은 pytest 임시 디렉터리만 사용한다. 기존 개발/수동 테스트 DB는 사용하지 않았다.

- 전체 인증·연습·TXT 업로드·녹음 업로드·설정: **298 passed, 4 skipped**.
  네 skip은 SQLite 조합에서 PostgreSQL 전용 검사를 제외한 것이다.
- 설정 테스트 35건(실제 PostgreSQL 32건, 파일시스템·OpenAPI 3건)이 통과했다. 본인만 삭제/다른 사용자 유지,
  분석 결과·피드백 cascade, 미인증·만료·변조·signup 토큰 거부, 기존 access token
  보호 API 차단, 반복/동시 탈퇴, 부분 파일 정리 실패와 영속 journal 재개를 검사했다.
- journal 준비/DELETE/commit 실패 및 commit acknowledgement 유실을 주입했다.
  실제 PostgreSQL reports DELETE trigger에서 오류를 발생시켜 cascade 중간 실패의
  전체 rollback, HTTP 503, 원본 파일 보존, 정상 재시도도 검증했다.
- 업로드 파일 복사 중 탈퇴와 잠긴 업로드 완료 대기를 검사했다. 후자는
  `pg_blocking_pids`로 실제 잠금 대기를 확인하고 늦게 커밋한 녹음까지 정리했다.
- 삭제 후 분석 UPDATE 0행/INSERT FK 거부, 복구 중 DB 접근 실패 시 파일 보존,
  중복 복구와 이미 없는 파일의 안전한 재처리를 검사했다.
- 신규 DELETE와 기존 인증·TXT·녹음 경로가 OpenAPI에 함께 등록되는 것을 확인했다.
- `git diff --check` 및 새 파일의 공백 검사를 실행했다.

실행하지 않은 검증: 실행 중인 실제 BE2 워커 취소(현재 구현 없음), 실제 프로세스
강제 종료/전원 장애, 운영 스케줄러·외부 저장소. 파일시스템 장애는 예외 주입으로
검증했으며 실제 디스크 장애를 재현한 것은 아니다. journal은 새 객체로 다시 읽어
복구했고, 프로세스 재기동 자체를 재현한 테스트는 아니다.


## 최종 코드 리뷰에서 강화한 사항

- API의 커밋 후 정리와 모든 복구 프로세스는 동일 저널 디렉터리 inode에 대한
  POSIX `flock(LOCK_EX)`로 직렬화한다. 준비 작업도 같은 잠금을 사용한다.
  잠금 대기 중 다른 작업자가 완료해 저널이 없어졌다면 이미 처리한 작업으로 간주한다.
  여러 프로세스가 각각 같은 작업을 완료로 셀 수 있으므로 completed는 전역 고유 건수가 아니다.
- 저널은 `version`, `job_id`, `user_id`, `paths`, `checksum`만 저장한다.
  토큰·이메일·이름·대본·분석 결과는 저장하지 않는다. 사용자 ID와 파일 경로는
  복구에 필요한 최소한의 계정 연결 정보이므로 비공개로 보존한다.
- 스키마·타입·작업 파일명과 ID의 일치·SHA-256 체크섬을 검사한다.
  체크섬은 우발적 손상 감지용이며 서명이나 인증 수단이 아니다.
  신뢰된 운영자 권한을 탈취한 공격자가 목록과 체크섬을 모두 재작성하는 상황은
  방어 범위 밖이다. 이 권한이면 DB·음원 자체도 변경할 수 있다.
- 모든 경로를 삭제 전에 일괄 검증한다. 저장소 바로 아래의 정규화된 절대 경로와
  기존 UUID 파일명/확장자만 허용한다. 심볼릭 링크·하드 링크·디렉터리 등은 거부한다.
  사용자 부재뿐 아니라 목록의 어떤 경로도 현재 recordings에 참조되지 않는지 확인한다.
  다른 사용자의 살아 있는 파일을 가리키면 앞의 정상 파일도 지우지 않고 전부 보류한다.
- 파일과 저널 디렉터리는 `O_NOFOLLOW`와 디렉터리 FD를 사용한다. 파일 삭제도
  디렉터리를 고정한 `unlink`로 수행해 링크 대상이나 다른 디렉터리를 따라가지 않는다.
  이미 없는 파일/작업의 반복 처리는 안전하며, 손상된 작업은 삭제 없이 pending으로 남긴다.
- 저널 디렉터리는 서비스 UID 소유·0700, 저널은 같은 UID 소유·0600이어야 한다.
  녹음 디렉터리는 서비스 UID 소유이며 그룹/다른 사용자 쓰기 권한이 없어야 한다.
  기존 객체가 이 조건을 어기거나 링크면 자동 권한 변경 없이 실패한다.
- 임시 파일 쓰기·파일 fsync·원자적 rename·디렉터리 fsync 각각에 실제 예외를
  주입해, 준비 단계 실패 시 DB cascade가 시작되지 않고 파일이 보존되는지 확인했다.
- 두 개의 독립 spawn 프로세스를 Barrier로 동기화해 같은 작업을 동시에 복구했다.
  API가 DB를 커밋한 직후 복구가 먼저 파일을 정리하는 경합도 검사했다.
  전체 회귀 테스트와 OpenAPI의 기존 경로·중복 operationId 검사도 통과했다.

## 필수 운영 조건

- POSIX 로컬 파일시스템에서 directory flock, directory fsync, 원자적 rename,
  O_NOFOLLOW/dir_fd 동작이 지원되어야 한다. Windows에서는 무조건 fcntl을
  import해 앱 전체 기동을 깨뜨리지 않지만 탈퇴 기능은 이 잠금 지원이 없으면 503으로 거부한다.
  로컬 저장소의 강화된 삭제도 POSIX용이다. Windows에서의 파일 정리·탈퇴는 지원 검증하지 않았다.
- API 프로세스와 복구 프로세스가 **동일한 실제 볼륨·절대 root 경로·DB·서비스 UID**를
  사용해야 한다. NFS나 서로 다른 볼륨을 사용하는 여러 서버로 확장할 때는 이 보장을
  적용하지 말고 분산 잠금/저장소 계약을 별도 설계한다.
- uploads/recordings 전체(숨김 저널과 준비 중 임시 파일 포함)를 영속 볼륨에 둔다.
  재배포 시 이미지의 임시 파일시스템으로 대체하거나 폴더를 비우면 안 된다.
  root와 상위 경로를 신뢰된 서비스/운영자 외에는 변경·rename할 수 없게 하고,
  실행 중에는 잠금 대상인 저널 디렉터리를 제거·교체하지 않는다.
- 같은 절대 경로를 다른 데이터에 재사용하거나 녹음 경로를 수동으로 재참조하지 않는다.
  DB/볼륨 시점 불일치 복원, UID/경로 변경, 버전 없는 이전 형식 저널은 자동으로
  재해석하지 않는다. 안전하게 pending으로 남기고 운영자가 실제 참조를 대조한다.
- 주기 복구·재시작 후 복구 실행과 pending/503/로그 감시가 필요하다. 사용자에게는
  `ACCOUNT_DELETED_CLEANUP_PENDING`이 **이미 계정이 삭제된 상태**임을 안내한다.
  프론트는 토큰·사용자/연습 캐시를 지우고 “계정은 삭제되었으며 녹음 파일 정리가
  지연되고 있습니다”처럼 안내한다. 일반 DELETE 재요청(401 가능)을 파일 정리
  재시도로 사용하지 않는다. 운영자는 복구 CLI로 정리하며, 프론트용 완료 조회 API는 없다.
